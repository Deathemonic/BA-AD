# Contributing to BA-AD

Keep contributions focused, readable, and consistent with the existing code.

## Setup

Install Git, Rust with edition 2024 support, and your platform's compiler and linker.
Fork and clone the repository. Check local dependency paths in the [workspace manifest](Cargo.toml).

```sh
rustup toolchain install nightly
rustup component add --toolchain nightly rustfmt clippy
```

## General guidelines

- **SOLID:** Keep responsibilities focused, interfaces small, and dependencies decoupled.
- **KISS:** Choose the simplest implementation that solves the problem.
- **DRY:** Reuse existing logic instead of duplicating it.
- **YAGNI:** Do not build for hypothetical future needs.

- Follow surrounding patterns. Keep changes small and leave unrelated code alone.
- Keep the FFI side in sync. Mirror affected API and behavior changes in the C API and UniFFI bindings in the same PR, and validate both bindings rather than only the Rust or CLI side.
- Use clear names, small functions, early returns, and named constants. Avoid comments that merely restate code.
- Separate logical phases with a single blank line. Formatting alone does not make code readable.
- Keep declarations before implementations and free functions last. Group imports by standard library, external dependencies, then project imports.
- Keep module indexes limited to declarations and re-exports. Do not create a module folder for a single implementation file.
- Keep fields private unless needed externally. Avoid forwarding getters and unnecessary abstractions.
- Preserve validation and source errors. Use typed library errors, not panics or silently ignored failures.
- Avoid unnecessary clones and allocations. Reuse existing dependencies and derives before hand-writing equivalent code.
- Discuss new dependencies, major features, and breaking API changes first. Keep single-consumer dependencies local to their crate.
- Do not suppress warnings, weaken lint settings, or edit [Cargo.lock](Cargo.lock) by hand.

## Validation

Run these from the repository root, one at a time:

```sh
cargo build
cargo +nightly fmt --all
cargo +nightly clippy --workspace --all-targets --all-features
```

Use nightly for formatting and Clippy, and keep Cargo's default build directory.

**Do not add tests.** Validate changes through actual runs against the game services and data.
The game changes frequently; focus on working implementations rather than perfecting fixed test expectations.
Report the command, region/platform, and result. For fixes, reproduce the issue and confirm it is resolved. State anything not checked.

## Pull requests

### Review priority

1. **High:** Fixes and chores that address bugs, maintenance, or small cleanup.
2. **Medium:** Features.
3. **Lowest:** Full refactors or broad rewrites, even when labeled as chores.

### Submission requirements

- One problem per PR. Review your diff and update affected callers and documentation.
- Keep the description short: what changed, why, and how you verified it. No essays or filler.
- Understand your changes and be ready to explain them.

Use branches starting with `feat/`, `fix/`, or `chore/`. Keep commits focused, with lowercase summaries prefixed by `feat:`, `fix:`, or `chore:`. Use `ci:` for CI-only changes and `merge:` for PR titles.

Changes that ignore these requirements may be returned for revision or closed.
